# 관리자 가이드

서비스 관리 콘솔(`/admin`)에서 다루는 설정 가운데 동작을 알고 써야 하는 것을
적는다. 화면 구성은 [사용자 가이드 §2.9](guide.md#29-서비스-관리-콘솔-admin),
배포와 환경 변수는 [오프라인 배포](OFFLINE.md)를 본다.

## 메일 알림 (SMTP)

**메일 알림** 탭에서 사내 SMTP 릴레이를 가리키면 사람이 기다리는 일이 생겼을
때 메일이 간다. 기본은 **꺼짐**이다. 새로 설치한 곳에서는 아무것도 달라지지
않고, 관리자가 켜기 전까지 어떤 메일도 나가지 않는다.

### 설정 표

설정 행은 `settings` 표의 `mail:smtp` 이고, 관리 API 는 `PUT /api/v1/admin/settings/mail`
이다. 키 이름은 사내 메일 표준과 같다 — 다른 사내 서비스(kanpic 등)와 같은 이름을
쓰므로 한 번 배우면 된다.

| 키 | 기본값 | 뜻 |
| --- | --- | --- |
| `mail.enabled` | `false` | 꺼짐이 기본. 관리자가 켠다 |
| `mail.smtp_host` | — | 사내 릴레이 주소. 켜려면 반드시 필요하다 |
| `mail.smtp_port` | `25` | 사내 릴레이는 대개 25. 465 면 `security` 가 `auto` 일 때 `tls` 로 본다 |
| `mail.security` | `auto` | `auto` · `none` · `starttls` · `tls`. `auto` 는 서버가 STARTTLS 를 알리면 쓰고 아니면 평문 |
| `mail.skip_tls_verify` | `false` | 사내 인증서가 사설일 때만 |
| `mail.username` · `mail.password` | 빈 값 | 인증 없는 릴레이가 흔하므로 **선택 사항**. 비어 있으면 AUTH 를 시도하지 않는다 |
| `mail.from_address` · `mail.from_name` | — · `Orbit` | 보내는 사람. 주소를 비우면 `orbit@<smtp_host>` |
| `mail.base_url` | — | 메일 속 "바로 열기" 링크가 가리킬 이 앱의 주소. 비우면 링크를 넣지 않는다 |
| `mail.timeout_seconds` | `10` | 연결·전송 제한 시간(1~120) |
| `mail.notify_approval_request` | `true` | 검토 요청 알림 스위치 |
| `mail.notify_approval_decided` | `true` | 검토 결과 알림 스위치 |
| `mail.notify_account_created` | `true` | 계정 준비 알림 스위치 |

**비밀번호는 되읽히지 않는다.** 설정을 읽으면 `has_password` 로 "설정됨" 여부만
돌아오고, 화면에도 그렇게만 보인다. 바꾸려면 새 값을 넣어 저장하고, 지우려면
"저장된 비밀번호 제거"를 켜고 저장한다. 비밀번호는 다른 비밀(OIDC Client Secret,
AI API Key)과 같은 봉투 암호화로 따로 보관되며 로그에 남지 않는다.

폐쇄망에서는 릴레이 주소로 사내 메일 서비스 `postra` 를 가리키면 알림이 밖으로
나가지 않는다.

### 시험 발송

설정을 **저장한 뒤** "시험 발송" 칸에 받는 주소를 넣고 누르면 저장된 설정으로
실제 한 통을 보내고 결과를 그 자리에서 보여 준다. 받는 사람은 관리자 자신의
주소가 기본값이다. 릴레이 설정은 한 번에 맞는 일이 드무니, 켜고 나서 반드시 한 번
보내 본다. 실패하면 릴레이가 돌려준 응답(연결 거절, 인증 실패, 수신 거부 등)이
그대로 보인다. 시험 발송도 발송 기록에 남고 감사 로그에 `mail.test` 로 적힌다.

흔한 실패:

- `SMTP 연결 실패 … connection refused` — 호스트·포트가 틀렸거나 컨테이너에서
  릴레이로 가는 길이 막혀 있다.
- `서버가 인증을 지원하지 않습니다` — 사용자 이름을 넣었는데 릴레이가 AUTH 를
  제공하지 않는다. 사용자 이름을 비운다.
- `STARTTLS 실패 … certificate` — 사설 인증서다. `skip_tls_verify` 를 켜거나
  `security` 를 `none` 으로 둔다.
- `RCPT TO 실패` — 릴레이가 그 주소로의 중계를 거부한다. 릴레이 쪽 허용 목록을 본다.

### 보내는 이벤트와 고른 이유

기준은 하나다 — 이 메일이 오지 않으면 누군가 화면을 계속 새로고침하거나 손해를
본다. 단순한 "무언가 바뀜"은 보내지 않는다.

| 이벤트 | 받는 사람 | 왜 |
| --- | --- | --- |
| `approval.requested` 검토 요청 | 관리자 전원과, 검토자 역할이 팀장이면 팀장 전원 | 승인 프로세스가 켜진 곳에서 검토자는 누가 무엇을 올렸는지 알 길이 `/approvals` 를 열어 보는 것뿐이다. 요청자는 그동안 기다린다 |
| `approval.decided` 검토 결과 | 요청한 사람 | 승인·반려는 요청자가 기다리는 결과다. 반려 사유가 있으면 함께 간다 |
| `account.created` 계정 준비 | 관리자가 만든 계정의 주인(메일 주소가 있을 때) | 계정을 부탁한 사람은 언제 들어갈 수 있는지 모른다. 사용자 ID 와 로그인 주소만 보내고 비밀번호는 싣지 않는다 |

기억 본문은 어떤 메일에도 싣지 않는다. 본문은 사용자 키로 암호화된 것이고, 검토자는
화면에서 자기 권한으로 본다.

시끄럽지 않게 하는 규칙:

- **자기가 한 일은 자기에게 보내지 않는다.** 관리자가 자기 기억을 올리거나 자기
  요청을 처리하면 그 알림은 나가지 않는다.
- **잇달아 올라온 검토 요청은 묶는다.** 같은 검토자에게 15분 안에 검토 요청 메일이
  이미 나갔으면 다시 보내지 않고, 첫 메일에 "검토를 기다리는 요청이 모두 N건"을
  적는다. 검토 결과는 묶지 않는다 — 요청자마다 자기 결과를 기다린다.
- 이벤트 종류별 스위치로 한 종류만 끌 수 있다.

### 발송 기록

**메일 알림** 탭 아래의 발송 기록(`GET /api/v1/admin/mail/deliveries?status=`)은
시도마다 한 줄이다 — 언제, 어떤 이벤트로, 누구에게, 무슨 제목으로 보냈고 되었는지
안 되었는지. 실패만 남기면 "안 왔다"는 문의에 답할 수 없으므로 성공도 남긴다.
본문은 담지 않는다. 설정이 켜져 있어도 호스트가 비어 있으면 보내지 않고 그 이유가
`failed` 줄에 남는다.

### 요청을 막지 않는다

메일은 배경에서 보낸다. 릴레이가 느리거나 죽어 있어도 기억 등록·검토·사용자 생성
요청은 평소처럼 성공하고, 발송만 `failed` 로 기록된다. 잠깐 연결을 거절하는
릴레이를 위해 2초 뒤 한 번 더 시도한다.

### 사용자 명부

메일 기능은 자기 사용자 표를 갖지 않는다. 받는 사람은 `users` 표의 `email` 로
정하며, 주소가 비어 있거나 비활성인 계정은 조용히 건너뛴다. 알림을 받게 하려면
**사용자** 탭에서 메일 주소를 채운다.

### 확인 절차 (사람이 한 번)

1. 관리 콘솔 → 메일 알림에서 릴레이 주소를 넣고 켠 뒤 저장한다.
2. 시험 발송으로 자기 주소에 한 통 보내고 받은 것을 확인한다.
3. 승인 프로세스를 켠 상태에서 멤버 계정으로 기억을 올리고, 팀장 계정의 메일함에
   "검토 요청"이 오는지, 처리한 뒤 멤버에게 "검토 결과"가 오는지 본다.
4. 릴레이를 끊어 놓고(호스트를 틀린 값으로 바꾸어) 같은 일을 반복해 요청이
   평소처럼 끝나고 발송 기록에 `failed` 만 남는지 본다.
